# セキュリティ
- AWSなどの機密情報（アクセスキー・トークン・パスワード等）は出力しないでください
- 機密情報をコードやファイルに追加するときは、必ず .gitignore に追加してください

# 環境（このマシンの前提）
- Apple Silicon (M4 Max)。Homebrew は /opt/homebrew (arm64) を使う。/usr/local の旧 Homebrew (x86_64) は撤去待ちのため参照・変更しない
- `incompatible architecture (have 'x86_64')` 系のエラーは Rosetta 時代の残骸が原因。ネイティブ成果物の再ビルド/再取得（node_modules 再install 等）で対処する
- ターミナルマルチプレクサは herdr（tmux から移行済み。tmux 設定は凍結中で削除しない）
- エディタは nvim（EDITOR=nvim）
- Docker Compose は `docker compose`（v2）を使う。`docker-compose`（ハイフン付き v1・pyenv 経由の x86_64）は使わない
- node のバージョン管理は nvm に集約する（nodebrew は nvim の LSP 用に凍結、brew の node@18/20 は互換用。新規セットアップで増やさない）
- Terraform の lock 更新は複数プラットフォーム指定で行う（`terraform providers lock -platform=darwin_arm64 -platform=linux_amd64`）。arm64 単独で lock を再生成すると CI が壊れる

# 開発方針
- 機能の実装には必ずテストを書いてください。原則TDD（テストファースト）で進めてください
- 既存ロジックを共通化・リファクタする際は、「挙動不変」をテストで担保してから切り出してください
- 破壊的操作（データ削除・アンインストール・サーバ/プロセスの強制終了・上書き等）は、実行前に必ず確認を取ってください

# Git / PR
- mainへ直接コミットせず、必ず作業ブランチを切ってからPRを作成してください
- 作業は小さな単位のブランチに分割し、Stacked PR（子ブランチのPRは親ブランチをbaseにする）で作成してください。コンテキストを細かく残すことを目的とします
- 親→子の順でマージします。親ブランチに変更が入ったら、子ブランチを忘れずにrebaseしてください
- 会話の中で指示されたら、確認を取らずに push / PR作成 / PRのマージ / ローカルブランチの削除まで進めてよい（リポジトリの所有者は問わない）
  - これは「指示されたことを止まらずにやりきってよい」という許可であって、指示されていない push / PR作成 / マージを先回りして行う許可ではない
  - 以下は引き続き実行前に確認する:
    - リモートブランチの削除（`git push --delete` / `git push origin :branch` / `gh pr merge --delete-branch`）
    - main や共有ブランチへの force push
    - 必須チェックが失敗しているPRを `--admin` でマージすること
- PRの本文は冒頭に「何をしたPRなのか」を記述してください
- 「Phase」などの作業段階を表す文言は使わず、実際に対応した内容のみを記述してください
